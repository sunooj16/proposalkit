# proposalkit 구현 기획

제안서 작성용 블록 기반 보조도구. Claude Code / Codex 환경에서 파일 기반으로 동작한다.

> 변경 이력은 부록 B 참조. v2의 미결 사항 4건은 모두 확정되어 본문에 반영되었고, 결정 근거는 12장에 기록되어 있다.

---

## 1. 문제 정의

여러 지원사업·IR·R&D 제안서를 반복 작성할 때 두 가지 문제가 발생한다.

1. **일관성 붕괴** — 과거 제안서를 복사해 수정하는 과정에서 회사의 핵심 주장이 문서마다 조금씩 달라진다.
2. **낡은 사실의 재생산** — 시장 수치, 실적, 정책 환경이 갱신되지 않은 채 계속 인용된다.

두 문제 모두 "무엇이 변해도 되고 무엇이 변하면 안 되는가"가 저장 구조에 표현되어 있지 않아서 생긴다.

### 파일 기반 환경의 전제

웹서비스였다면 권한 모델로 해결된다. 특정 필드를 read-only로 두면 끝이다.

파일 + LLM 에이전트 환경에서는 그것이 성립하지 않는다. 에이전트가 리포지토리 전체에 쓰기 권한을 갖고, frontmatter에 `editable: strict`라고 적어도 그것은 **부탁이지 강제가 아니다**.

따라서 설계의 중심 질문은 이렇게 이동한다.

> "어떻게 구분해 저장할까" → **"구분이 지켜지는지 어떻게 기계적으로 검증할까"**

저장 구조는 그 검증이 가능한 형태로 나와야 한다.

### 실행 환경 제약

- **Windows / PowerShell**이 주 환경이다.
- **git 훅에 의존하지 않는다.** 호환성 문제가 있고, 훅은 리포지토리를 클론한 다른 환경에 따라오지 않는다.
- **Claude Code 전용 기능에 의존하지 않는다.** Codex에서도 같은 방어선이 작동해야 한다. 두 환경의 공통 분모는 셸 명령이므로, 강제는 전부 `ppsk` CLI 안에 있어야 한다.

이 제약이 8장의 강제 장치 설계를 결정한다.

## 2. 데이터 분류 — 세 개의 축

### 축 1: 계층 (내용이 무엇인가)

| 계층 | 성격 | 갱신 트리거 | 신선도 주기 |
|---|---|---|---|
| **Identity** | 사실 — 우리는 누구인가 | 조직·자산 변동 시 | 없음 |
| **Thesis** | 주장 — 우리는 무엇을 주장하는가 | 증거가 반증할 때 | 180일 |
| **Evidence** | 근거 — 무엇으로 증명하는가 | 추가형 | 90일 |
| **Strategy** | 가설 — 어떻게 시장에 들어가는가 | 시장 검증 결과 | 180일 |
| **Execution** | 계획 — 이번 제안에서 무엇을 할 것인가 | 제안 건마다 | 해당 없음 |

**신선도 주기를 계층별로 나누는 이유:** 회사 소개문에 90일 경고를 띄우면 노이즈가 되고, 노이즈가 섞이면 Evidence 경고까지 같이 무시된다. 경고는 무시당하는 순간 없는 것과 같으므로, 뜨는 경고는 전부 볼 가치가 있어야 한다.

> **주의: Thesis는 사실이 아니라 주장이다.** Identity와 같은 칸에 넣고 "불변"으로 규정하면, 검증에서 흔들린 주장을 시스템이 계속 재생산한다. 필요한 것은 불변이 아니라 **변경 비용이 높은 상태**다. Thesis는 변경 시 어떤 증거 때문에 바꿨는지 기록을 남긴다(8장 `ppsk core-update`).

### 축 2: 편집 등급 (도구가 무엇을 해도 되는가)

| 등급 | 의미 | 검증 방식 |
|---|---|---|
| `strict` | 문장 그대로 인용. 재작성 금지 | 블록 본문이 초안에 축자 등장하는지 대조 (공백 정규화) |
| `free` | 의미 유지하며 재작성 허용 | 검증 없음 |

v1의 4등급(`verbatim` / `rephrase` / `select` / `generate`)에서 축소했다. 이유:

- `verbatim`은 수치·등록번호를 뜻했는데, 그것은 이미 `facts.yaml`로 분리된다(6장). 블록 레벨에 남을 일이 거의 없다.
- `generate`의 대상인 Execution은 `core/` 밖에 있어 애초에 이 축의 대상이 아니다.
- `rephrase`와 `select`의 차이는 **기계적으로 검증할 수 없다.** 에이전트가 지킬 뿐이다. 검증 불가한 값을 스키마에 두면 "선언했으니 지켜지겠지"라는 착각이 생긴다.

`strict`만 남긴 대신 그것은 **실제로 검사한다.** 스키마 필드는 검증되거나, 검증되지 않는다면 검증되지 않는다고 명시되거나 둘 중 하나다.

두 축이 모두 필요한 이유는 그대로다. Identity 계층 안에도 재작성 가능한 서술("훈련 소재를 개인화하는 엔진")과 손대면 안 되는 문구(법인 정식 명칭, 인증 표기)가 섞여 있다.

---

### 축 3: 프로젝트 (어느 사업에 속하는가)

회사에 프로젝트가 여럿이면 같은 리포지토리 안에 서로 무관한 주장과 수치가 섞인다. 계층이나 태그로는 이것을 가를 수 없다 — **계층은 "무엇인가", 태그는 "얼마나 관련 있는가", 프로젝트는 "여기에 들어가도 되는가"** 다. 앞의 둘은 정렬이고 이것은 차단이다.

```yaml
projects: [cogtrain]      # 이 프로젝트 전용
# projects 생략               → 전 프로젝트 공용
```

- **생략이 공용이다.** 회사 소개·팀·보유자산처럼 실제로 공용인 블록이 다수이므로, 공용을 기본값으로 두고 전용만 명시한다.
- 프로젝트 어휘는 `projects.yaml`로 통제한다. **미등록 프로젝트 id는 처음부터 실패다** — 태그와 달리 오타가 곧 조용한 빈 결과이기 때문이다.
- 필터링은 정렬보다 먼저 일어난다. 다른 프로젝트 전용 블록은 점수가 아무리 높아도 후보에 들어오지 않는다.

프로젝트를 태그로 표현하지 않는 이유가 여기 있다. 태그는 가중치로 순위를 매기는 부드러운 장치이고, 프로젝트는 A 사업의 실적이 B 사업 제안서에 새어 들어가는 것을 막는 단단한 장치다. 같은 필드에 두 성질을 섞으면 결국 둘 다 흐려진다.

리포지토리를 프로젝트별로 나누지 않는 이유는 기획 전체의 전제와 같다. 회사 소개와 팀 구성은 모든 프로젝트에서 동일하고, 복제하면 반드시 어긋난다.

## 3. 블록 원자 단위

**파일 하나 = 개념 하나.** 길이는 가변이며, 두 문장짜리 파일과 한 페이지짜리 파일이 공존해도 된다.

### 분할 판정 기준

1. 다른 제안서에서 **통째로 넣거나 통째로 뺄 수 있는가.** 절반만 쓰고 싶어진다면 두 개념이다.
2. 제목을 한 문장으로 붙일 수 있는가.
3. **파일 안에서 `editable` 등급이 갈리는가.** 가장 기계적인 신호.

```
core/thesis/
├── problem-definition.md      # 어떤 문제가 중요한가
├── existing-limitation.md     # 기존 방식은 왜 부족한가
├── core-claim.md              # 우리는 무엇이 다른가
└── capability-basis.md        # 왜 우리가 해결할 수 있는가
```

개념 단위로 쪼개면 파일 수가 늘어난다. frontmatter의 `summary`를 모아 `INDEX.md`를 생성하는 `ppsk index`가 사실상 필수다. 에이전트는 인덱스를 먼저 읽고 필요한 파일만 연다.

### 블록 상태

임포트로 생성된 블록은 신뢰도가 낮다. 그것이 `core/`에 들어가는 순간 잠기면, 검토되지 않은 문장이 그대로 굳는다.

```yaml
status: draft    # 임포트 직후 기본값. 잠금 대상 아님. 사용 시 경고.
status: active   # 사람이 검토·승인. 잠금 대상.
```

## 4. 디렉터리 구조

```
proposalkit/
├── CLAUDE.md                  # → docs/rules.md 참조 (한 줄 포인터)
├── AGENTS.md                  # → docs/rules.md 참조 (한 줄 포인터)
├── INDEX.md                   # 자동 생성 — 전체 블록 summary
├── facts.yaml                 # 모든 수치의 단일 소유자 (분할 시 facts/*.yaml)
├── tags.yaml                  # 통제 어휘 + alias
├── projects.yaml              # 프로젝트 등록부 (id, 이름, 상태)

│   ├── identity/

│   │   └── assets.md
│   └── thesis/

│       ├── core-claim.md
│       └── capability-basis.md
├── evidence/
│   ├── research/
│   ├── validation/
│   └── market/
├── strategy/
│   ├── active/
│   └── archive/
├── templates/
│   ├── angles/                # rnd.md, ir.md, commercialization.md
│   └── schemas/               # 제안 유형별 고정 슬롯
├── proposals/
│   └── 2026-08-tips-rnd/

│       ├── angle.md           # 이번 건의 강조점 결정        ← 사람이 씀
│       ├── draft.md           # 초안 소스 ({{fact}} 미치환)  ← 에이전트가 씀
│       ├── final.md           # ppsk build 산출물               ← 자동 생성
│       ├── report.md          # 검증 리포트                   ← 자동 생성 (읽기 전용)
│       └── deviations.md      # core 이탈 시도 로그           ← 자동 기록
├── archive/                   # 과거 제안서 원본 (컨텍스트 제외)
├── .claude/

└── ppsk/                        # CLI 본체
```

`CLAUDE.md`와 `AGENTS.md`를 각각 한 줄 포인터로 두고 규약을 `docs/rules.md` 하나에 모으는 이유: 두 파일을 따로 관리하면 반드시 어긋난다.

**`draft.md`와 `final.md`를 분리하는 것이 6장 수치 검증의 전제다.** 검증은 `draft.md`에만 적용되고, `final.md`는 검증을 통과한 결과물이다. 하나의 파일에 두 역할을 맡기면 "치환된 숫자"와 "지어낸 숫자"를 구별할 수 없다.

## 5. 블록 스키마

```yaml
---
id: thesis-core-claim
layer: thesis                  # identity | thesis | evidence | strategy
status: active                 # draft | active
editable: free                 # strict | free
last_verified: 2026-07-10
facts_used: [patent_personalization, pilot_n_2025]
tags: [기술난제, 개인화, 인지훈련]     # tags.yaml의 정규형
projects: [cogtrain]           # 생략하면 전 프로젝트 공용 (2장 축 3)
summary: 기존 개인화는 난이도 조절에 머물러 있고 우리는 훈련 소재를 개인화한다
---
```

`projects.yaml`:

```yaml
_config:
  unassigned: notice          # 소속 미선언 블록의 등급. notice | warn | error

cogtrain:
  name: 인지훈련 개인화
  status: active              # active | archived
  aliases: [cog, 인지훈련]

ncore:
  name: N-Core 플랫폼
  status: active
```

`archived` 프로젝트의 블록은 수집에서 제외되지만 파일은 남는다 — 지우면 이력이 사라지고, 남겨두기만 하면 매번 후보에 낀다.

**제거된 필드 (v1 대비)**

- `mutability` → `editable` 2등급으로 축소 (2장)
- `valid_until` → 블록에서 제거. 만료는 fact의 속성이며 블록은 인용한 fact로부터 상속한다 (6장)
- `angles` → 제거. 앵글 매칭은 `tags`로 단일화한다 (7장). 같은 정보를 두 필드로 표현하면 반드시 어긋난다.

`summary`는 `INDEX.md` 생성에 사용된다. 별도 매니페스트를 유지하는 것보다 각 파일 frontmatter에서 스크립트로 뽑아 쓰는 편이 동기화 문제가 없다.

## 6. 수치 — facts.yaml 단일 소유

모든 수치를 본문에서 분리해 `facts.yaml`에 모은다. 갱신 지점이 한 곳으로 모이고, 초안의 숫자가 등록된 값인지 기계 검증이 가능해진다.

```yaml
pilot_n_2025:
  value: "참여자 42명"
  num: 42                   # 파생 계산에 쓰일 때만 필수
  source: "2025 요양병원 파일럿 결과보고서 p.7"
  verified: 2026-06-01
  stability: volatile
  recheck_days: 90

total_sessions_2025:
  value: "누적 1,008세션"
  num: 1008
  source: "플랫폼 로그 집계 2025-12-31"
  verified: 2026-06-01
  stability: volatile
  recheck_days: 90

patent_personalization:
  value: "10-2024-XXXXXXX"
  source: "특허등록원부"
  verified: 2025-11-20
  stability: fixed          # 재확인 주기 없음

market_size_kr:
  value: "3,200억 원"
  source: "보건산업진흥원 2025 보고서"
  verified: 2025-09-01
  stability: volatile
  recheck_days: 180
```

`valid_until`은 `stability` + `recheck_days`로 통합했다. 두 필드가 같은 축("이 값이 언제까지 믿을 만한가")을 중복 표현했기 때문이다. 판정 규칙도 하나가 된다 — `fixed`는 영구 통과, `volatile`은 `verified + recheck_days`가 지났으면 재확인 대상.

### 파생 fact — 최소 지원

"1인당 2.4회" 같은 계산값은 등록도 면제도 정확하지 않다. 등록하면 입력값이 바뀌어도 조용히 남고, 면제하면 검증 대상에서 빠진다. 계산식을 선언하되 **범위를 좁게 묶는다.**

```yaml
sessions_per_user_2025:
  expr: "total_sessions_2025 / pilot_n_2025"
  format: "1인당 {v:.1f}회"
```

지원 범위:

| 허용 | 금지 |
|---|---|
| 등록된 fact id, 십진 리터럴 | 함수, 조건식, 문자열 연산 |
| `+ - * /`, 괄호 | 다른 파생 fact 참조 (깊이 1 고정) |
| `format`의 `{v}` 슬롯 1개 + 정밀도 | 다중 슬롯, 조건부 포맷 |

**파생 fact는 `verified` / `stability` / `recheck_days` / `source`를 선언할 수 없다.** 선언하면 `ppsk check`이 실패시킨다. 이 금지가 이 기능의 핵심이다 — 파생값에 독립적인 확인 일자를 허용하면, 방금 확인한 파생값 뒤에 1년 묵은 입력값이 숨는다.

대신 전부 상속한다.

- `verified` — 입력 중 **가장 오래된** 것
- 재확인 기한 — 입력 중 **가장 먼저 도래하는** 것
- `source` — 입력들의 출처 + 계산식 (자동 생성)

`ppsk verify sessions_per_user_2025`는 거부된다. 입력 fact를 확인하라는 안내와 함께 해당 id 목록을 출력한다.

값은 캐시하지 않고 `ppsk build` 시점에 계산한다. 캐시가 없으면 캐시가 낡을 일도 없다.

### Evidence 블록과 fact의 경계

| | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| `facts.yaml` 항목 | 값, 출처, 확인 일자 | 해석·서술 |
| Evidence 블록 | 그 값이 무엇을 뜻하는지의 서술 | 값 자체 (`facts_used`로 참조) |

Evidence 블록은 `verified` 날짜를 자체적으로 갖지 않는다. 인용한 fact의 상태를 상속한다.

### 본문 참조 문법

```markdown
파일럿 참여자 {{pilot_n_2025}} 중 {{completion_rate_2025}}가 8주 과정을 완료했으며,
{{sessions_per_user_2025}}를 수행했다.
1차년도 {{!12개월}} 동안 TRL {{!6}}단계까지 도달한다.
```

- `{{fact_id}}` — 등록된 수치 참조. `ppsk build`가 치환한다.
- `{{!텍스트}}` — **면제 마커.** fact가 아닌 수치임을 명시. 그대로 출력된다.

### 검사 대상 숫자 클래스

"`facts.yaml`에 없는 숫자가 초안에 나타나면 즉시 오류"를 문자 그대로 적용하면 **1차년도, TRL 6단계, 12개월, 표 2, 3가지 접근**에서 수십 건이 오탐으로 뜨고, 그 시점에 게이트가 꺼진다. 검사는 **주장성 수치**로 한정한다. 위반은 **오류**다.

| 대상 | 예 |
|---|---|
| 금액 | 3,200억 원 / 1.2조 / $500K |
| 규모·실적 | 42명 / 17건 / 8개 기관 |
| 비율·배수 | 34% / 2.3배 / 12%p |
| 등록번호 | 10-2024-XXXXXXX / 사업자번호 / DOI |

| 제외 | 예 |
|---|---|
| 순번·구조 | 1., 제2장, 표 3, 그림 4 |
| 기간·연차 | 12개월, 1차년도, 3주 |
| 단계·등급 | TRL 6단계, 3단계 구성 |
| 목록 개수 | 3가지 방법, 두 축 |
| 날짜 | 2026-08-01 |

근사·범위 표현("약 3배 수준", "월 10만 원대")은 **대상**이다. 근사값이라도 주장을 지탱하므로 출처가 있어야 하며, `value`에 근사 표현 그대로 담아 등록한다.

남는 오탐은 `{{!...}}`로 면제하되, **`ppsk check`이 면제 사용 건수를 리포트한다.** 면제가 늘어나면 숫자 클래스 정의가 잘못된 것이므로, 남용이 보이는 상태여야 한다.

### facts.yaml 확장 — 로더를 먼저 열어둔다

수치가 100건을 넘어가면 단일 YAML은 diff는 되지만 사람이 훑기 어렵다. 다만 지금 분할하는 것은 이르다. 대신 **로더가 처음부터 양쪽을 지원한다.**

```
facts/ 디렉터리가 존재하면  → facts/*.yaml 전부 병합해 로드
없으면                     → facts.yaml 단일 파일 로드
```

fact도 프로젝트에 속한다. 파일 단위로 기본 소속을 선언하면 항목마다 반복하지 않아도 된다.

```yaml
# facts/cogtrain.yaml
_project: cogtrain            # 이 파일의 모든 fact 기본 소속

pilot_n_2025:
  value: "참여자 42명"
  ...
```

fact id는 전역 유일이므로 분할해도 `{{fact_id}}` 참조 문법은 바뀌지 않는다. 즉 마이그레이션은 **파일 이동 한 번**이며 본문 수정이 없다. `ppsk check`은 항목 수가 80건을 넘으면 분할 검토 알림을 한 줄 출력한다(실패 아님).

**결정을 미룰 때는 마이그레이션 비용을 먼저 0으로 만든다.** 그래야 미루는 것이 부채가 아니라 판단 유예가 된다.

## 7. 앵글 처리 — 파생 텍스트를 저장하지 않는다

`core/`에는 원본 하나만 존재한다. 앵글별 파생 텍스트는 어디에도 저장하지 않는다.

**이유:** 앵글별 파생 파일을 저장하면 원본이 바뀔 때 파생본이 낡는다. 그런데 git diff는 이를 잡아주지 않는다 — 파생 파일은 수정되지 않았으니 조용히 남아 있다가, 반년 뒤 폐기된 주장이 제안서에 들어간다.

대신 앵글은 **지시**로만 남긴다.

### angle.md — 경로가 아니라 의도로 쓴다

블록 경로를 우선순위 순으로 나열하게 하면 두 가지 문제가 생긴다. 사람이 판단해야 할 것은 "이번 공고는 기술적 난제를 앞세워야 한다"이지 "`core/thesis/existing-limitation`을 1순위로"가 아니고, 블록을 추가하거나 이름을 바꾸면 모든 `angle.md`가 조용히 깨진다.

```markdown
<!-- proposals/2026-08-tips-rnd/angle.md -->
---
proposal_type: rnd
project: cogtrain                 # 이 제안서가 속한 프로젝트. 생략하면 회사 단위(IR 등)
extends: templates/angles/rnd.md
generated_from:                   # ppsk collect가 기록
  - core/thesis/existing-limitation.md@8c1e04b
  - core/thesis/core-claim.md@a3f21c9
  - core/identity/team.md@1d90f77
---

## 강조
- tag:기술난제 (강)
- tag:성능목표 (강)
- tag:신규성 (강)
- tag:시장규모 (배경)

## 고정 포함
- core/thesis/core-claim        # 태그와 무관하게 반드시 포함

## 제외
- strategy/pricing
- strategy/gtm
```

`ppsk collect`가 태그 가중치로 블록을 정렬하고, 고정 포함/제외를 덮어쓴다. **존재하지 않는 경로나 어떤 블록도 매칭되지 않는 태그는 실패로 처리한다.**

### 태그 어휘 통제

앵글 매칭이 태그로 단일화되면서 태그가 설계의 부하를 진다. 자유롭게 늘어나면 `기술난제` / `기술적난제` / `난제`가 공존하고 매칭이 조용히 흐려진다. **통제 어휘 + alias**로 묶되, **초기 강제 수준은 경고**다.

```yaml
# tags.yaml
_config:
  unregistered: warn          # warn | error — 안정화 후 error로 승격

기술난제:
  aliases: [기술적난제, 난제, technical-challenge]
  note: 해결이 어려운 기술적 문제 자체. 성능 목표와 구분할 것

성능목표:
  aliases: [성능지표, KPI, 목표성능]

시장규모:
  aliases: [시장크기, TAM]
```

- `ppsk index`와 `ppsk collect`가 alias를 정규형으로 치환한 뒤 매칭한다. 블록이 `난제`로 태깅되고 `angle.md`가 `tag:기술난제`를 요구해도 매칭된다.
- 미등록 태그는 경고이며, `ppsk check`이 **미등록 태그와 등장 횟수를 리포트한다.** 두세 번 이상 나온 태그는 어휘로 승격할 후보다.
- 어휘가 안정되면 `unregistered: error` 한 줄로 승격한다. 승격 시점을 코드 수정 없이 옮길 수 있는 형태로 둔다.

경고에서 시작하는 이유: 어휘를 먼저 확정하고 태깅을 시작하면 실제로 쓰이지 않는 태그를 설계하게 된다. 어휘는 임포트 결과에서 **귀납**되어야 한다(13장 1단계).

단, 참조 무결성은 별개다. `angle.md`의 태그가 미등록이면서 **동시에** 어떤 블록과도 매칭되지 않으면 그것은 경고가 아니라 실패다 — 오타로 인해 조용히 빈 결과가 나오는 것을 막아야 한다.

### generated_from — 전체 커밋이 아니라 블록별 해시

core 전체의 커밋 해시 하나를 기록하면, 쓰지도 않은 블록이 바뀌어도 모든 과거 초안에 경고가 뜬다. **실제 수집된 블록의 경로+해시 목록**으로 좁혀야 신호가 된다.

### 제안 유형별 강조점 참고

| 유형 | 전면에 내세울 것 |
|---|---|
| R&D 사업 | 기술적 난제, 알고리즘, 성능 목표, 신규성 |
| 사업화 사업 | 고객 문제, 시장 규모, 가격, 유통, 매출 가능성 |
| MVP 지원사업 | 현재 기술 수준 → 구현 범위 → 고객 검증 |
| 투자제안서 | 시장 크기 → 경쟁우위 → 확장성 → 성장 가능성 |
| 산학협력 | 대학 기술 활용 → 기술이전 → 사업화 연결 |

Core는 동일하고 Proposal Angle만 달라진다. 반복되는 유형은 `templates/angles/`에 두고 `extends`로 상속한다.

## 8. 검증과 강제

### 확인은 제안서가 아니라 fact가 소유한다

확인 체크박스를 제안서 폴더에 두면 같은 `market_size_kr`을 세 건에서 쓸 때 세 번 확인해야 하고, 확인 이력이 아무 데도 남지 않는다. **확인은 제안서의 속성이 아니라 fact의 속성이다.**

```bash
ppsk verify market_size_kr --note "2026 보고서 p.31 재확인, 값 변동 없음"
  → facts.yaml의 verified 갱신
```

이 하나로 세 가지가 정리된다.

- 확인 결과가 누적된다. 다음 제안서에서 같은 fact는 자동 통과한다.
- 체크리스트가 보통 두세 건으로 줄어 **실제로 확인하게 된다.** "통과 의례가 된 게이트"가 구조적으로 예방된다.
- `stability: fixed`(특허번호, 설립일)는 영구 통과이므로 등급화가 따로 필요 없다.

`report.md`는 체크박스가 아니라 **자동 생성 읽기 전용 리포트**다. 사람이 편집하는 파일이 아니다.

```markdown
<!-- proposals/2026-08-tips-rnd/report.md — 자동 생성 -->

## 재확인 필요 (2건)

- `market_size_kr` — 3,200억 원
  출처: 보건산업진흥원 2025 보고서
  마지막 확인 2025-09-01 (352일 경과, 주기 180일)
  사용 위치: draft.md L41
  → ppsk verify market_size_kr

- `sessions_per_user_2025` — 1인당 2.4회 (파생)
  입력: total_sessions_2025, pilot_n_2025
  가장 오래된 입력 확인 2026-06-01 (78일 경과, 주기 90일) ← 12일 남음
  사용 위치: draft.md L67

## 면제 마커 사용 (4건)
draft.md L12, L28, L55, L91

## 미등록 태그 (2건)
현장검증 (3회), 규제대응 (1회)   → tags.yaml 승격 후보

## draft 상태 블록 사용 (1건)
evidence/validation/pilot-2025-interpretation.md

## 알림
core 검토 권고 — 누적 deviation 4건 (임계 3건)
```

### 인라인 마커

터미널 경고는 스크롤에 묻히지만 문서 안의 주석은 편집하다 반드시 마주친다. `ppsk build --preview`가 해당 위치에 마커를 남긴다.

```markdown
시장 규모는 <!-- ⚠ 재확인 필요: market_size_kr -->3,200억 원으로
```

`ppsk build`(preview 아님)는 마커가 남아 있으면 변환을 거부한다.

### core 잠금 — 훅이 아니라 lock 파일로

git 훅은 이 환경에서 제약이 있고, Claude Code PostToolUse 훅은 Codex에서 돌지 않는다. "공통 분모는 셸 명령"이라고 해놓고 강제를 특정 도구 전용 기능에 맡기는 것은 자기모순이다.

**`core.lock`** — `core/` 파일별 SHA 목록. `ppsk check`이 대조한다. 훅 없이, 어느 에이전트에서도, 어느 OS에서도 동일하게 작동한다.

```yaml
# core.lock — ppsk core-update가 갱신
core/thesis/core-claim.md: a3f21c9...
core/identity/company.md: 1d90f77...
```

훅은 **선택적 조기 경보**로 강등한다. 있으면 편하고, 없어도 방어선은 유지된다.

### 정당한 변경 경로

"막기"만 있고 "바꾸기"가 없으면, 첫 제안서를 쓰다 `core-claim.md`가 어색하다는 것을 깨달은 순간 우회하거나 잠금을 끄게 된다. **막힌 사람이 우회로를 찾게 만드는 게이트는 게이트가 아니다.**

```bash
ppsk core-update core/thesis/core-claim.md --reason "파일럿 결과가 난이도 조절 대비 우위를 지지하지 않음"
  → core.lock 갱신
  → core/CHANGELOG.md에 일자·사유·diff 요약 기록
```

같은 이유로 `deviations.md`도 규약이 아니라 코드가 쓴다. "에이전트가 기록하도록 규약에 명시한다"는 부탁이며 원칙 1을 스스로 어긴다. `ppsk check`이 core 불일치를 감지하면 시도된 diff와 함께 자동 append한다.

### core 검토 루프 — 이벤트 기반 + 정기 백스톱

core를 잠그면 그 압력이 `deviations.md`에 쌓인다. 쌓이기만 하고 반영 절차가 없으면 core는 "낡지 않은 것"이 아니라 **"낡은 채로 고정된 것"**이 된다. 두 개의 트리거를 둔다.

| 트리거 | 조건 |
|---|---|
| 이벤트 | 미처리 deviation 누적 3건, 또는 **동일 core 블록에 대한 이탈 2회** |
| 백스톱 | 마지막 검토일로부터 90일 경과 |

동일 블록 반복이 건수보다 강한 신호다. 서로 다른 세 블록에서 한 번씩 벗어난 것은 제안서 특성일 수 있지만, 같은 블록에서 두 번 벗어난 것은 그 블록이 틀렸다는 뜻이다.

```bash
ppsk review            # 전체 proposals/를 스캔해 deviation을 core 블록별로 묶어 출력
ppsk review --close    # 검토 완료 기록 → CHANGELOG, 처리된 deviation 아카이브
```

`--close`가 처리된 항목을 `deviations.md`에서 걷어내는 것이 중요하다. 걷어내지 않으면 카운트가 영구 누적되어 알림이 상시화되고, 상시화된 알림은 무시된다.

**강제 수준은 알림이다. `ppsk check`을 실패시키지 않는다.** 검토를 게이트로 걸면 core 재설계를 제안서 마감 직전에 강요하게 되는데, 그 타이밍에 내려지는 Thesis 변경 결정은 가장 나쁜 결정이다. 검토는 제안서 작업 밖에서 일어나야 한다.

| deviation 임계 도달 또는 검토 백스톱 경과 | 알림 |
| `facts` 항목 수 80건 초과 | 알림 |
| 소속 미선언 블록·fact (공용으로 취급) | 알림 (`unassigned: error`로 승격 가능) |
| 면제 마커 사용 | 리포트 |

검증기는 **LLM 호출 없이 결정론적으로** 동작해야 한다. 검증까지 LLM에 맡기면 초안을 쓴 것과 같은 판단이 같은 실수를 통과시킨다.

## 9. 도구 구현 형태

### 역할 분담

가장 흔한 실패는 스크립트 안에 LLM 호출을 넣는 것이다. Claude Code 세션 안에서 이미 에이전트가 돌고 있는데 그 안에서 또 API를 호출하면 컨텍스트가 이중으로 관리되고 디버깅이 불가능해진다.

**작성은 에이전트가 한다. 도구는 앞뒤만 담당한다.**

| 담당 | 하는 일 |
|---|---|
| 결정론적 코드 (`ppsk`) | 인덱스 생성, 블록 수집, 태그 정규화, `{{fact}}` 치환·계산, 검증, 잠금 대조, 스캐폴딩 |
| 에이전트 (LLM) | 공고문 해석, 앵글 제안, 블록 선별, 재작성, 초안 작성, 임포트 분해 |

### 형태: 단일 CLI + 얇은 커맨드 래퍼

MCP 서버는 과잉이다. 파일시스템 접근은 에이전트가 이미 갖고 있으므로 프로토콜 계층을 추가할 이유가 없다. 기능은 전부 `ppsk` CLI에 넣고 슬래시 커맨드는 호출만 하게 두면 Claude Code와 Codex 양쪽에서 그대로 돌아간다.

### 명령 구성

```bash
ppsk init                           # 골격 생성
ppsk import <file>                  # 과거 제안서 → 블록·fact·태그 후보 스캐폴드
ppsk index                          # frontmatter summary → INDEX.md (태그 정규화 포함)
ppsk new tips-rnd --type rnd        # proposals/ 스캐폴드 + angle 템플릿 상속
ppsk collect tips-rnd               # angle.md 해석 → 필요한 블록만 stdout
ppsk check tips-rnd                 # 전체 검증
ppsk verify <fact-id> [--note ...]  # facts의 verified 갱신 (파생 fact는 거부)
ppsk build tips-rnd [--preview]     # {{fact}} 치환·계산 → final.md (검증 통과 시)
ppsk core-update <path> --reason    # core.lock 갱신 + CHANGELOG 기록
ppsk review [--close]               # deviation 취합 → core 검토
```

`ppsk resolve`는 `ppsk build`에 흡수했다. 치환만 하고 게이트를 통과하지 않은 중간 산출물은 쓸 데가 없다. 미리보기가 필요하면 `--preview`가 마커를 남긴 채 렌더링한다.

`ppsk collect`가 실질적으로 가장 중요하다. 개념 단위로 쪼개면 블록이 수십 개가 되는데, 에이전트가 전부 읽으면 컨텍스트가 낭비되고 정확도가 떨어진다. `angle.md`의 태그 가중치와 필터를 코드로 해석해 필요한 파일만 한 덩어리로 출력하면, 에이전트는 그것만 읽고 작성한다. **선별 판단 중 규칙으로 표현 가능한 부분을 코드로 내리는 것.**

### 강제 장치 3단

1. `docs/rules.md` — 계층별 권한 선언. 대체로 지켜지지만 보장 없음.
2. `.claude/hooks/` — 선택. Claude Code에서만 동작하는 조기 경보.
3. **`ppsk check`** — 실제 방어선. 환경 무관.

## 10. 작업 흐름

```
/new-proposal tips-rnd
  → 공고문을 brief.md에 붙여넣기

에이전트: brief.md 읽고 평가항목 추출 → angle.md 강조 태그 제안
사람:    angle.md 확정                     ← 핵심 판단 지점 ①

ppsk collect tips-rnd
에이전트: 초안 작성 → draft.md ({{fact}} 참조로 작성)

ppsk check tips-rnd
  ✗ 미등록 수치 1건 (draft.md L34: "17개 기관")
  ✗ 재확인 주기 경과 1건 (market_size_kr, 352일)
  ⚠ 미등록 태그 1건 (현장검증)
  ⚠ draft 상태 블록 1건
  ℹ core 검토 권고 — 누적 deviation 4건

사람:    수치를 facts에 등록하거나 {{!}}로 면제
         ppsk verify market_size_kr           ← 핵심 판단 지점 ②
         → 재실행 → 통과

ppsk build tips-rnd
  → final.md
```

반복 작업에서 사람이 개입하는 지점은 두 곳으로 고정된다. 경고와 알림은 흐름을 멈추지 않는다.

여기에 제안서 작업 **밖에서** 비정기적으로 두 가지가 발생한다.

- `ppsk core-update` — 주장이 실제로 흔들렸을 때. 빈도가 높다면 core가 아직 안정화되지 않았다는 신호다.
- `ppsk review` — 이벤트 트리거 또는 90일 백스톱. 알림은 제안서 작업 중에 뜨지만, **처리는 마감 뒤로 미루는 것이 정상**이다.

## 12. 결정 기록

v2까지 열려 있던 항목의 확정 내용과 근거.

### (1) 주장성 수치 클래스 — 규칙 기반 분류 + 파생 fact 최소 지원 · **오류**

전량 검사는 오탐으로 게이트를 폐기시키고, 검사 포기는 방어선을 없앤다. 규칙 기반 분류가 그 사이의 유일한 지점이며, 오탐 잔여분은 `{{!}}` 면제 + 사용량 리포트로 관측한다. 파생값은 계산식으로 등록하되 **확인 일자를 못 갖게 막는 것**이 요점이다 — 파생값이 독립적으로 "확인됨" 상태가 되면 낡은 입력이 그 뒤에 숨는다. 강제 수준을 오류로 두는 근거는, 이 규칙이 에이전트가 지어낸 수치를 잡는 **유일한 결정론적 방어선**이라는 것이다. 경고로 두면 존재 이유가 사라진다. (반영: 6장)

### (2) 태그 어휘 통제 — 통제 어휘 + alias · **경고 → 추후 오류**

앵글 매칭이 태그에 의존하게 되면서 어휘 표류가 곧 매칭 실패가 된다. 다만 어휘를 먼저 확정하면 실제로 쓰이지 않는 태그를 설계하게 되므로, 어휘는 임포트 결과에서 귀납한다. 그래서 초기 경고 → 안정화 후 `tags.yaml`의 `unregistered: error` 한 줄로 승격. 승격 시점을 코드 수정 없이 옮길 수 있게 설정값으로 둔 것이 핵심이다. 단 참조 무결성(매칭 0건)은 처음부터 오류다. (반영: 7장)

### (3) deviations → Thesis — 이벤트 기반 + 정기 백스톱 · **검토 알림**

정기 검토만 두면 압력이 쌓인 채 다음 주기까지 방치되고, 이벤트만 두면 임계에 안 닿는 느린 노후화를 놓친다. 둘 다 둔다. 이벤트 신호는 건수보다 **동일 블록 반복**이 강하다. 강제 수준을 알림으로 제한한 이유는 타이밍이다 — 검토를 게이트로 걸면 Thesis 변경 결정이 제안서 마감 직전에 내려진다. `--close`로 처리 항목을 걷어내지 않으면 알림이 상시화되어 무시되므로, 아카이브가 이 루프의 필수 부품이다. (반영: 8장)

### (4) facts 확장 — 단일 파일 유지, 임계치 도달 시 분할 · **보류**

지금 분할하면 쓰지도 않을 도메인 경계를 먼저 정하게 된다. 대신 로더가 `facts/` 디렉터리와 `facts.yaml` 단일 파일을 모두 지원하고, fact id가 전역 유일이므로 마이그레이션이 파일 이동 한 번으로 끝난다. **결정을 미룰 때는 마이그레이션 비용을 먼저 0으로 만든다.** 80건 초과 시 알림. (반영: 6장)

### 여전히 열려 있는 것

이 네 건은 닫혔지만, 1단계 임포트에서 다음이 확정되어야 한다.

- **계층 정의** — 5계층 중 어디에도 안 들어가는 문단이 나오면 그것이 계층 정의를 수정할 신호다.
- **숫자 클래스 경계** — 6장 분류표는 가설이다. 실제 표현 습관에 맞춰 조정한다.
- **초기 태그 어휘** — `tags.yaml`의 첫 목록은 임포트 결과에서 나온다.

## 13. 구현 순서

빈 리포지토리에 블록 20~30개를 손으로 쓰는 것으로 시작하면, 그 몇 시간짜리 데이터 입력 작업 앞에서 대부분 멈춘다. 그런데 임포트는 코드가 거의 필요 없다 — 분해는 에이전트가 하고 `ppsk`는 스캐폴드만 만든다.

### 1단계 — 임포트로 씨앗 만들기

- `ppsk init`, `ppsk import`, `ppsk index` 구현
- 과거 제안서 **2건** 투입 → 에이전트가 블록·fact·태그 후보 추출 → 사람이 승인/폐기/병합
- 모든 블록은 `status: draft`로 생성. 승인한 것만 `active`
- **계층 태깅이 안 되는 문단을 기록한다.** 그것이 계층 정의를 수정할 신호다
- `tags.yaml` 초안 작성 — 임포트에서 실제로 나온 태그를 정규형으로 확정하고, 변형은 alias로 흡수. `unregistered: warn`으로 시작
- 6장 숫자 클래스를 이 결과로 확정

이 단계의 산출물은 코드가 아니라 **채워진 리포지토리**다.

### 2단계 — 조립 경로

- `ppsk new`, `ppsk collect`, `ppsk check`, `ppsk verify`, `ppsk build` 구현
- 파생 fact 최소 지원(`num`, `expr`, `format`) — 실제로 필요한 계산값이 나온 뒤에 붙인다
- facts 로더를 단일 파일 / `facts/` 디렉터리 양쪽 지원으로 구현
- 실제 제안서 1건을 처음부터 끝까지 작성
- 여기서 드러난 문제로 스키마 조정

### 3단계 — 잠금과 검토 루프

- `core.lock`, `ppsk core-update`, `deviations.md` 자동 기록
- `ppsk review` — 이벤트 트리거 + 90일 백스톱
- 태그 어휘 안정화 확인 후 `unregistered: error` 승격 검토
- 선택적 훅 설정

**잠금이 마지막인 이유:** 안정화되지 않은 core를 먼저 잠그면, 그 잠금은 정당한 수정을 막는 방해물이 된다. 그 상태에서 사람은 우회로를 찾고, 우회가 습관이 되면 3단계가 끝나도 방어선은 작동하지 않는다. 잠글 가치가 생긴 다음에 잠근다. 검토 루프를 같은 단계에 두는 것도 같은 이유다 — 잠금과 검토는 한 쌍이며, 잠금만 있고 검토가 없는 기간이 길수록 우회가 학습된다.

## 부록 A: 설계 원칙 요약

1. **불변성은 저장 속성이 아니라 검증 대상이다.** frontmatter의 선언은 부탁이고, `ppsk check`이 강제다.
2. **규약은 짧게, 강제는 코드로.** 규칙 하나를 추가할 때마다 "이걸 코드로 검사할 수 있나"를 먼저 묻는다. 검사 불가능하면 스키마에서 빼거나, 검사하지 않는다고 명시한다.
3. **진실의 원본은 항상 하나다.** 파생 텍스트를 저장하지 않는 이유, 수치를 `facts`로 모으는 이유, 파생값을 캐시하지 않는 이유.
4. **검증에 LLM을 쓰지 않는다.** 초안을 쓴 것과 같은 판단은 같은 실수를 통과시킨다.
5. **Thesis는 사실이 아니라 주장이다.** 불변으로 못 박지 말고 변경 비용을 높게 둔다.
6. **강제는 환경에 의존하지 않는다.** 특정 에이전트나 OS에서만 작동하는 방어선은 방어선이 아니다.
7. **막힌 사람에게 정당한 출구를 준다.** 출구 없는 게이트는 우회를 학습시킨다.
8. **게이트는 통과 가능해야 실제 게이트다.** 매번 열 건씩 뜨는 확인 목록은 일괄 통과되고, 그 순간 없는 것보다 나빠진다.
9. **결정을 미룰 때는 마이그레이션 비용을 먼저 0으로 만든다.** 그래야 보류가 부채가 아니라 판단 유예가 된다.
10. **파생물은 확인 상태를 소유하지 않는다.** 소유하는 순간 원본의 노후화를 가린다.
11. **어휘와 규칙은 사용에서 귀납한다.** 먼저 확정한 분류는 쓰이지 않는 칸을 만든다.

## 부록 B: 설계 변경 이력

### v1 → v2

| 영역 | v1 | v2 | 이유 |
|---|---|---|---|
| 수치 검증 | 등록 안 된 숫자 전부 오류 | 주장성 수치로 한정 + `{{!}}` 면제 | 오탐 수십 건 → 게이트 폐기 |
| 산출물 | `draft.md` 하나 | `draft.md`(소스) / `final.md`(산출) | 치환된 숫자와 지어낸 숫자 구별 불가 |
| 확인 소유권 | 제안서의 체크박스 | fact의 `verified` + `ppsk verify` | 같은 값을 매번 재확인, 이력 미보존 |
| 만료 표현 | `valid_until` + `stability` | `stability` + `recheck_days` | 같은 축 중복 |
| 편집 등급 | 4등급 | `strict` / `free` 2등급 | 4개 중 검증 가능한 것이 없었음 |
| 앵글 지정 | 블록 경로 우선순위 나열 | 태그 가중치 + 고정 포함/제외 | 사람이 파일시스템 관리자가 됨 |
| 앵글 필드 | `angles` + `tags` | `tags` 단일 | 같은 정보 이중 표현 |
| 신선도 경고 | 전 계층 90일 | 계층별 주기 | 경고 피로 → 전체 무시 |
| core 스냅샷 | core 전체 커밋 해시 | 사용된 블록별 해시 | 무관한 변경에 전부 경고 |
| core 잠금 | git 훅 + Claude Code 훅 | `core.lock` + `ppsk check` | Windows/Codex에서 미작동 |
| core 변경 | 경로 없음 | `ppsk core-update --reason` | 출구 없어 우회 유발 |
| deviations | 에이전트가 기록하도록 규약 | `ppsk check`이 자동 기록 | 부탁은 강제가 아님 |

| 참조 무결성 | 검증 없음 | 미매칭 경로·태그 실패 | 블록 개명 시 조용히 깨짐 |
| 블록 상태 | 없음 | `status: draft \| active` | 임포트 블록이 검토 없이 잠김 |
| 명령 | resolve/build 부재·분리 | `build` 단일 + `--preview` | 최종 변환 단계가 명령에 없었음 |
| 임포트 | 3단계 | 1단계 | 수동 입력 30건이 진입 장벽 |
| 잠금 | 2단계 | 3단계 | 안정화 전 잠금은 우회를 학습시킴 |
